오늘은 싸피 일과 중 JavaScript의 `this`, 객체와 프로토타입을 학습했다. 강사님과는 앞으로 무엇을 해야 할지 고민하던 내용에 대해 상담을 진행했다.

## JavaScript의 this

오늘 학습하며 정리한 핵심은 일반 함수의 `this`가 함수를 정의한 위치만으로 결정되지 않고, **어떻게 호출하는지에 따라 달라진다**는 점이다.

```javascript
const person = {
  name: "철수",
  introduce() {
    return this.name;
  },
};

console.log(person.introduce()); // "철수"
```

위 코드에서는 `person.introduce()`로 호출하므로 `this`가 `person`을 가리킨다. 하지만 메서드를 다른 변수에 담아 일반 함수처럼 호출하면 같은 결과를 보장하지 않는다.

### 브라우저의 전역 객체 window와 strict mode

브라우저의 전역 객체 이름은 `windows`가 아니라 `window`다. 환경에 관계없이 전역 객체에 접근할 때는 `globalThis`를 사용할 수 있다.

아래 예제는 브라우저의 일반 `<script>`에서 실행하는 것을 기준으로 한다. 모듈이나 실행 도구에 따라 결과가 달라질 수 있으므로 실행 환경도 함께 확인해야 한다.

```html
<script>
  console.log(this === window); // true: 일반 스크립트의 최상위 this

  function normalFunction() {
    return this;
  }

  function strictFunction() {
    "use strict";
    return this;
  }

  console.log(normalFunction() === window); // true
  console.log(strictFunction()); // undefined
</script>
```

일반 함수를 `fn()`처럼 단독으로 호출하면, 비엄격 모드에서는 `this`가 전역 객체로 대체된다. strict mode에서는 이러한 대체가 일어나지 않아 `undefined`가 된다. 메서드를 변수에 담아 호출할 때도 이 차이를 주의해야 한다.

```javascript
function checkDetachedMethod() {
  "use strict";

  const person = {
    name: "철수",
    introduce() {
      return this.name;
    },
  };

  console.log(person.introduce()); // "철수"

  const introduce = person.introduce;
  introduce(); // TypeError: this가 undefined이므로 name에 접근할 수 없다.
}

// checkDetachedMethod()를 실행하면 마지막 호출에서 오류가 발생한다.
```

다만 **strict mode라고 해서 모든 위치의 `this`가 `undefined`가 되는 것은 아니다.** 브라우저의 일반 스크립트 최상위에서는 `"use strict"`를 사용해도 `this`가 `window`다. 객체의 메서드로 호출하면 strict mode에서도 해당 객체를 가리킨다.

반면 `<script type="module">`과 같은 ES 모듈에서는 기본적으로 strict mode가 적용되고, 최상위 `this`도 `undefined`다. 전역 객체가 필요하면 `window`나 `globalThis`로 명시적으로 접근하면 된다.

### 화살표 함수는 바깥 스코프의 this를 사용한다

화살표 함수는 자신의 `this`를 만들지 않고, **정의된 위치를 둘러싼 스코프의 `this`를 사용한다.** 일반 함수처럼 호출 방식에 따라 `this`가 바뀌지 않는다.

```javascript
const person = {
  name: "철수",
  makeIntroduce() {
    return () => this.name;
  },
};

const introduce = person.makeIntroduce();
console.log(introduce()); // "철수"
console.log(introduce.call({ name: "영희" })); // "철수"
```

`person.makeIntroduce()`의 `this`는 `person`이다. 그 안에서 만든 화살표 함수도 이 `this`를 사용하므로, 나중에 단독으로 호출해도 `person.name`을 읽는다. `call`, `apply`, `bind`로 화살표 함수 자체의 `this`를 바꿀 수도 없다.

그렇다고 객체 안에 화살표 함수를 작성하면 그 객체가 `this`가 되는 것은 아니다. **객체 리터럴 자체는 새로운 `this` 바인딩을 만들지 않는다.**

```html
<script type="module">
  const person = {
    name: "철수",
    getThis: () => this,
  };

  console.log(person.getThis()); // undefined: 모듈 최상위의 this
</script>
```

같은 코드를 브라우저의 일반 스크립트 최상위에 작성하면 화살표 함수는 바깥의 `this`인 `window`를 사용한다. 객체의 프로퍼티로 호출했다는 이유만으로 `person`을 가리키지는 않는다.

앞으로 `this`를 확인할 때는 일반 함수인지 화살표 함수인지, 어떻게 호출했는지, 일반 스크립트인지 모듈인지, strict mode가 적용되는지를 함께 살펴봐야겠다.

참고: [MDN — this](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Operators/this), [MDN — Strict mode](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Strict_mode), [MDN — globalThis](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/globalThis)

## 객체와 프로토타입

객체에서 프로퍼티를 찾을 때는 먼저 객체 자신이 가지고 있는지 확인하고, 없으면 프로토타입 체인을 따라 탐색한다.

```javascript
const person = {
  greet() {
    return `${this.name}입니다.`;
  },
};

const student = Object.create(person);
student.name = "철수";

console.log(student.greet()); // "철수입니다."
```

`student`에는 `greet`가 직접 정의되어 있지 않다. 하지만 프로토타입으로 연결된 `person`에서 메서드를 찾아 실행할 수 있다. 이때 `student.greet()`로 호출했으므로 메서드 내부의 `this`는 `student`를 가리킨다.

이 예제를 통해 프로퍼티를 **어디에서 찾는지**와 메서드를 **어떤 객체를 통해 호출하는지**를 구분해서 정리해 보았다.

### Java의 static과 비슷하다고 느꼈던 부분

프로토타입을 배우면서 처음에는 Java의 `static`과 비슷한 느낌이라고 생각했다. 여러 인스턴스가 공통으로 사용하는 메서드를 한곳에 둔다는 점이 비슷하게 느껴졌기 때문이다.

다만 둘을 같은 개념으로 이해하면 안 된다. Java의 `static` 메서드는 클래스에 속하지만, JavaScript의 프로토타입 메서드는 인스턴스가 프로토타입 체인을 따라 찾아 사용한다. 일반적인 메서드 호출에서 `this`도 호출한 인스턴스를 가리킨다.

따라서 프로토타입 메서드는 **여러 인스턴스가 공유하는 인스턴스 메서드**로 이해하는 편이 더 정확하다. JavaScript에도 별도로 클래스의 `static` 문법이 있다는 점을 구분해 두려고 한다.

## 강사님과의 상담

오늘은 앞으로 무엇을 해야 할지에 대한 고민을 가지고 강사님과 상담을 진행했다. 평소 생각하던 고민을 말로 꺼내고, 앞으로의 방향에 대해 이야기를 나누는 시간이었다.

### 채용공고를 기준으로 공부의 우선순위 정하기

우선 내가 취업하려는 포지션의 채용공고를 분석하고, 여러 공고에서 공통으로 요구하는 기술스택을 찾아보기로 했다. 그 기술을 중심으로 프로젝트를 진행하는 것이 지금의 우선순위다. CS 공부는 면접이 잡혔을 때 면접 준비와 함께 집중해서 진행하는 방향으로 조언을 받았다.

지금까지 내가 본 채용공고에서는 다음과 같은 기술과 도구가 눈에 들어왔다. 아직 충분히 분석한 결과는 아니므로, 공고를 더 모으면서 어떤 요구사항이 반복되는지 확인해야 한다.

- 프론트엔드 및 AI 활용: TypeScript, React, Next.js, LLM API, Claude Code 등의 AI 개발 도구 활용
- 백엔드: FastAPI, Spring, Django

프로젝트도 아이디어부터 정하기보다는 채용공고에서 요구하는 기술스택을 먼저 보고 방향을 잡아보라는 이야기를 들었다. 특히 관심이 가는 회사가 있다면, 그 회사의 기술스택과 서비스에 맞춰 프로젝트의 기술과 아이디어를 구체화하는 방법도 있다.

백엔드 공부 역시 풀스택 개발자 채용공고까지 살펴보면서 필요한 기술을 찾고, 프로젝트에 적용하는 식으로 접근해 보려고 한다. FastAPI나 Django도 막연히 공부할 목록에 추가하기보다, 지원하려는 공고와 연결해서 학습할 필요가 있다.

### 지원과 공부를 꾸준히 이어 갈 환경 만들기

프로젝트와 공부를 하면서 이력서도 꾸준히 넣어야 한다. 매일 한 곳 또는 이틀에 한 곳처럼 지속할 수 있는 지원 주기를 정해 두라는 조언을 받았다. 준비가 모두 끝나는 시점만 기다리기보다 지원을 병행하는 방향이다.

혼자 계획만 세우는 데서 그치지 않도록 저녁에 함께 공부할 팟을 구하고, 프로젝트를 같이 할 팀원도 찾아보려고 한다. 매일 싸피에 와서 무엇을 어떻게 공부할지 루틴을 만드는 것도 필요하다.

목표를 너무 먼 미래에만 두면 당장 무엇을 해야 할지 막막해진다. 목표를 잘게 나누고, 눈앞에 보이는 일을 하나씩 해 나가는 방식으로 바꿔 보고 싶다.

### 다른 교육생을 바라보는 마음가짐 바꾸기

잘하는 교육생을 보면 내가 도태된 것 같다는 느낌을 받을 때가 있다. 상담에서는 그들을 보며 초조해하기보다, 본받을 사람으로 바라보고 목표와 지향점으로 삼아 보라는 이야기를 들었다.

사람마다 장단점이 다른데, 다른 사람의 잘하는 부분을 보고 나 전체를 부족하다고 판단하고 있었던 것은 아닌지 돌아보게 된다. 잘한다, 못한다는 흑백논리로 비교하기보다 내가 배울 수 있는 부분을 찾는 쪽으로 마음가짐을 바꿔 보려고 한다.
