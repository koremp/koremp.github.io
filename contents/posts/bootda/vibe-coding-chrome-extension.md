사람인, 잡코리아, 원티드에 지원하다 보면 내가 어디에 무슨 직무로 지원했는지 다시 찾아보게 된다. 사이트마다 들어가서 확인하는 게 번거로워서, 지원 내역을 한곳에서 볼 수 있는 **붙다(BootDa)**를 만들었다. 처음부터 끝까지 Codex를 사용해서 바이브 코딩으로 만들었고, 웹앱은 Vercel에 배포했다. 지금은 `bootda.my`로 접속할 수 있다. [붙다 웹앱](https://bootda.my)

지원 기록을 직접 추가하고 수정하는 것부터 시작했다. 전형 단계별 칸반 보드와 회사별 메모, CSV 내보내기도 넣었다. 회사 홈페이지에서 직접 지원한 내역도 같이 관리하고, 잡플래닛 기업 페이지를 연결하면 평점과 리뷰 수도 볼 수 있게 했다.

근데 이미 채용 사이트에 있는 기록을 또 입력해야 하는 게 귀찮았다. 이걸 가져올 수 있으면 좋겠다는 생각에 크롬 확장 프로그램까지 만들게 됐다.

## 사이트를 만들다가 크롬 확장까지

확장은 로그인한 브라우저에서 지원 내역을 읽어서 붙다 계정으로 옮겨주는 역할을 한다. 처음에는 `chrome://extensions`에서 개발자 모드를 켜고 확장 폴더를 불러와서 확인했다. 코드를 고치면 확장과 페이지를 새로고침하고 다시 실행하는 식이었다.

같은 지원 내역인데도 사이트마다 가져오는 방식이 달랐다. 원티드는 목록만 읽어서는 공고 링크를 가져올 수 없어서, 회사명을 눌러 상세 창을 열고 링크를 읽은 다음 닫는 과정까지 넣었다. 창이 늦게 뜨거나 다음 페이지로 넘어가는 조건이 다르면 또 고쳐야 했다. AI에 실제 화면 구조를 전달하면서 수정하는 일이 계속됐다.

다른 사람도 설치해서 쓸 수 있게 GitHub Releases에 ZIP을 올리고, Chrome 웹 스토어 배포도 해봤다. 스토어에 올릴 소개와 이미지도 준비하고, 어떤 사이트에 접근하는지, 가져온 기록을 어디에 저장하는지 설명해야 했다. 웹사이트를 배포하면서 크롬 확장도 배포해보는 경험을 하게 됐다.

수정할 때마다 다시 올리는 과정은 GitHub Actions로 만들었다. 확장 버전을 올리고 릴리스 노트를 적은 뒤 태그를 푸시하면 ZIP을 만들고 스토어 심사에 제출하는 흐름이다. 웹앱을 먼저 배포해도 사용자에게는 이전 확장이 남아 있을 수 있어서, 두 쪽의 버전이 달라도 동작하는지도 챙겨야 했다.

## 다른 사람에게 써보라고 하니까

SSAFY 16기 소통방에 올릴 소개글도 다듬었다. 확장으로 이미 지원한 기록을 가져올 수 있고, 직접 입력하거나 CSV로 내보낼 수도 있다는 내용을 넣었다. 내가 만든 기능을 다른 사람에게 설명하려니 사용 순서부터 정리하게 됐다.

소개 페이지에는 30초 사용 영상과 확장 설치 배너, 계정 연결 방법을 넣었다. 확장을 설치하지 않고 수집 버튼을 누르면 설치 안내 팝업이 뜨도록 바꿨다. 배너를 닫았을 때 메뉴가 이동하는 위치 같은 것도 고쳤다. 이미 열어둔 탭에는 예전 화면이 남아서, 배포한 뒤 새로고침하고 다시 확인하는 일도 있었다.

그렇게 붙다를 반에 공유했는데... 회원가입부터 안 됐다. 강사님께 혼났고, 많이 부족하다는 생각이 들었다. 지원 내역 가져오는 기능까지 만들었는데 처음 들어온 사람은 가입부터 막혀서 써볼 수가 없었다.

원인을 확인해보니 Supabase Auth의 기본 메일 발송 서비스에 프로젝트 전체 시간당 두 통 제한이 있었다. 가입 확인이나 비밀번호 재설정에 쓰는 인증 메일의 발송 한도였다. 11월 10일 운영 로그에서도 가입 요청 네 건이 이메일 발송 한도 초과로 실패했다는 결과를 받았다.

로그인 테스트가 없었냐고 Codex에 물어봤다. 화면과 회원가입 모드 전환을 확인하는 테스트는 있었는데, CI에서는 가짜 인증 설정을 사용하고 있었다. 실제 메일을 받고 링크를 눌러 가입을 마치는 것까지는 확인하지 못했다. 테스트가 통과했다는 결과를 보고 어디까지 확인된 건지 더 물어봤어야 했다.

백엔드를 같이할 사람을 구해야겠다는 생각도 했다. 가입과 로그인부터 같이 살펴볼 사람이 있으면 좋겠다고 느꼈다. 다음에 누군가에게 링크를 공유하기 전에는 새 계정으로 가입하고 지원 기록 하나를 저장하는 데까지 직접 해봐야겠다.

## 메일 하나 보내는 것도 쉽지 않았다

메일 문제는 문의 페이지를 만들 때도 있었다. 운영팀 Gmail로 문의를 받고 싶었는데 앱 비밀번호 발급에서 본인 확인이 막혔다. 휴대폰과 데스크톱에서 해봐도 안 돼서, 일단 Formspree로 문의를 받도록 연결했다. 이쪽은 운영 페이지에서 테스트 문의를 보내고 Gmail 받은편지함에 도착하는 것까지 확인했다.

Gmail SMTP로 바꾸는 구현과 모의 테스트는 별도 초안 PR에 준비해뒀다. 앱 비밀번호를 발급받은 뒤 실제 발송을 확인하고 전환하는 작업은 남아 있다.

회원가입 인증 메일은 따로 발송 방법을 찾아봤다. 커스텀 SMTP와 Send Email Hook, 외부 메일 서비스도 알아보고 Google 로그인을 기본으로 둘까 하는 이야기도 했다. 비용을 아끼려고 하니 도메인이나 Gmail 앱 비밀번호 문제로 다시 돌아오기도 했다.

이후 `bootda.my`를 마련하고 Resend를 연결했다. 발송 도메인을 등록하고 가비아 DNS에 인증 레코드를 추가한 뒤, API 키를 만들어 Supabase의 Custom SMTP에 넣었다. 발신 주소는 `noreply@bootda.my`로 설정했다. 웹사이트에 도메인을 붙이는 것에 더해 메일을 보내기 위한 도메인 인증도 해야 했다.

11월 11일에는 SMTP 설정까지 마쳤고, 시간당 30통으로 시작하는 방안을 이야기했다. Supabase 쪽 설정과 Resend의 발송 한도를 같이 봐야 한다는 것도 알게 됐다. 새 이메일로 가입해서 인증 메일을 받고 서비스에 들어가는 과정은 아직 확인 결과를 더 남겨야 한다.

## 도메인을 바꾸면서 다시 손본 것들

`bootda.my`로 옮길 때도 손볼 곳이 많았다. 웹앱의 메타데이터와 사이트맵, Supabase 인증 URL, Google 인증 설정, 확장의 사이트 권한과 연결 주소를 바꿨다. 이전 Vercel 주소와 `www` 주소가 새 주소로 이동하는지도 확인했다.

확장에 저장된 기록도 있었다. 이전 주소에서 쌓인 로컬 기록과 동기화 대기 기록을 같은 계정과 운영 DB인지 확인한 뒤 옮기고, 새 주소에서 수정한 값도 보존하도록 했다. 주소를 바꾸는 일이 기존 데이터를 이어서 쓰는 문제까지 연결됐다.

이 변경을 PR로 올려 검증하고 병합한 뒤 확장 버전도 1.11.30으로 올렸다. 스토어 제출은 Google Cloud 인증 조건에서 한 번 막혀서, 수동 배포 워크플로와 인증 조건을 맞추고 다시 실행했다. 당시 마지막으로 확인한 상태는 업로드와 심사 제출을 마친 심사 대기였다.

그동안 설치 안내, 소개 영상, 문의 발송, 도메인 변경을 같이 작업해서 로컬 변경도 꽤 섞였다. 각각 브랜치와 PR로 나눠 올리고 리뷰와 검증을 거쳐 병합했다. 중간에는 Git 쓰기와 네트워크 접근이 막혀 대화를 여러 번 옮겨야 했다. 새 `bootda` 프로젝트에서 `previous_bootda`의 작업 기록을 가져와 이어가기도 했다. 어느 환경에서 작업 중이고 어디까지 반영했는지 확인하는 데도 시간이 들었다.

## 토큰이 다 떨어지니 내가 할 수 있는 게 없었다

처음부터 끝까지 Codex를 썼다. 코드 작성뿐 아니라 컴퓨터 사용 스킬로 어지간한 서비스 등록과 설정도 맡겼다. 직접 해야 할 것 같은 작업까지 해주니까 편했고, 계속 그렇게 진행했다.

근데 토큰이 다 떨어지고 나니 내가 개발할 수 있는 게 아무것도 없었다. 직접 등록하고 설정하는 과정까지 맡겨버려서, 혼자 이어가려니 어디서부터 해야 할지 막막했다. 만들어진 건 많은데 내가 얼마나 이해하면서 따라왔는지 돌아보게 됐다.

바이브 코딩으로 여기까지 만들어본 건 좋았다. 웹앱에 크롬 확장까지 배포해봤으니. 다만 다음에는 어떤 설정을 왜 바꿨는지, 문제가 생기면 어디를 봐야 하는지 정도는 직접 확인하면서 해봐야겠다. 토큰이 없어도 작은 수정은 할 수 있어야 할 것 같다.

## 이 글의 초안도 Codex로 썼다

이 회고도 Codex에 `bootda`, `previous_bootda` 대화를 읽고 내가 한 작업을 정리해달라고 해서 초안을 썼다. 작업 기록을 모으는 건 편했는데, 읽어보니 설명이 반복되는 부분도 있고 작업 보고서처럼 느껴지는 부분도 있었다.

그래서 반에 공유했다가 혼난 일, 백엔드를 구해야겠다고 생각한 것, 토큰이 떨어지고 나니 할 수 있는 게 없었던 이야기를 직접 덧붙였다. 그리고 다시 전체를 읽고 내 말투로 다듬어달라고 했다. 이 글도 그렇게 몇 번을 고치고 있다.

블로그를 시작할 때 글 쓰는 연습도 해야겠다고 했는데, 글 쓰는 것까지 Codex로 하니까 이것도 쉽지 않다... 내가 뭘 했는지 정리하는 것과 그때 무슨 생각이 들었는지 쓰는 건 각각 신경 써야 하는 것 같다. 다음에는 작업하면서 내 생각도 조금씩 적어둬야겠다.
